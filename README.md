## Постановка задачи

**Задача:** мультиклассовая классификация обращений в поддержку на 7 категорий.

**Бизнес-цель:** автоматический роутинг — нужно направить тикет в профильный отдел сразу при поступлении, без ручного ознакомления оператора с текстом. Это снижает время первого ответа и разгружает линию поддержки.

**Ключевая метрика — F1 macro.** Она усредняет F1 по классам **с равным весом** независимо от их размера. В нашей задаче это принципиально важно: класс `other` (4.5%) встречается в 6 раз реже, чем `payment` (25.2%), и F1 weighted / accuracy «замаскировали» бы плохие предсказания на редких классах.

Распределение классов:

| Категория    | Количество | Доля  | Описание |
|--------------|-----------|-------|----------|
| `payment`    | 2 516     | 25.2% | Проблемы с оплатой и подпиской |
| `bug`        | 1 987     | 19.9% | Технические неисправности |
| `moderation` | 1 621     | 16.2% | Вопросы по модерации анкет и фото |
| `account`    | 1 309     | 13.1% | Доступ к аккаунту, смена данных |
| `complaint`  | 1 307     | 13.1% | Жалобы на других пользователей |
| `refund`     | 815       | 8.2%  | Возврат средств |
| `other`      | 445       | 4.5%  | Прочее |

**Датасет несбалансированный** — пропорции классов отличаются в 5–6 раз. Учитываем это на всех этапах: стратифицированный сплит, F1 macro как целевая метрика, classification_report по каждому классу.

## Выбор признаков и борьба с утечкой данных

**Data leakage** — ключевая проблема при работе с реальными тикетами. В датасете много полей, которые *физически не могут быть известны* в момент создания тикета, но сильно коррелируют с категорией.

### Признаки, исключённые как утечка

| Признак | Почему утечка |
|---------|---------------|
| `resolution_time_minutes` | Появляется только ПОСЛЕ обработки тикета оператором |
| `escalated` | То же — флаг эскалации проставляется в процессе обработки |
| `csat_ticket` | Оценка пользователя после закрытия тикета |
| `support_response` | Ответ поддержки — отсутствует при поступлении |
| `priority` | В реальном продукте проставляется модерацией/автоклассификатором уже ПОСЛЕ создания, на основе категории — то есть является прямым производным целевой переменной |
| `sentiment_score` | Тональность — результат работы отдельной ML-модели, не приходит с тикетом |

Если бы модель видела `priority` или `sentiment_score`, она бы по ним почти однозначно восстанавливала `category` — F1 получался бы нереалистично высоким (0.99+) и не воспроизводился бы в продакшене.

### Признаки, исключённые по правке преподавателя

- **`day_of_week`** — день недели не несёт полезной информации о *типе* обращения: проблема с платежом одинаково вероятна в любой день. Исключаем, чтобы не добавлять шумовых OHE-колонок.
- **`created_at`, `registration_date`** — голые даты не используем как признаки: они уникальны для каждого тикета и ведут к переобучению. Информация о времени уже закодирована в `hour_of_day` и `days_since_registration`.

### Итоговый набор признаков

| Тип | Признаки |
|-----|----------|
| **Числовые (13)** | `hour_of_day`, `age`, `days_since_registration`, `total_likes`, `total_matches`, `messages_sent`, `active_days_last_week`, `boosts_purchased`, `superlikes_purchased`, `past_tickets_count`, `avg_csat_history`, `message_length_chars`, `message_length_words` |

## Предобработка данных

### Числовые признаки

**Пропуски.** Поле `avg_csat_history` пустое у новых пользователей без истории тикетов. Заполняем **медианой** по колонке: это нейтральное значение, не смещает распределение (в отличие от среднего, которое чувствительно к выбросам). Остальные числовые — без пропусков.

```python
for col in NUMERIC_FEATURES:
    X[col] = pd.to_numeric(X[col], errors="coerce").fillna(X[col].median())
```

### Категориальные признаки

**Пропуски** заменяем отдельной меткой `"unknown"` — так модель сможет учитывать **сам факт отсутствия значения** как сигнал (например, незалогиненный пользователь без `gender` может иметь специфичное распределение по категориям обращений).

**Кодирование:** One-Hot Encoding с `handle_unknown="ignore"` — каждая категория становится бинарной колонкой, новые значения в test-выборке просто зануляются (не ломают инференс). Почему OHE, а не OrdinalEncoder: между `Android` и `iOS` нет иерархии, они не сравнимы по порядку.

Для CatBoost категориальные **не кодируем вручную** — модель применяет к ним target encoding с ordered boosting (это её ключевая фича, см. раздел про CatBoost).

### Целевая переменная

`LabelEncoder` переводит строковые метки в целочисленные: `account=0, bug=1, complaint=2, ...` Сохраняем массив `CLASSES` с оригинальными именами для читаемого вывода метрик.

### Разбиение на train/test

```python
X_train, X_test, y_train, y_test = train_test_split(
    X, y_encoded, test_size=0.2, stratify=y_encoded, random_state=42
)
```

**80% train / 20% test, стратифицированно.** Стратификация (`stratify=y_encoded`) гарантирует одинаковые пропорции классов в train и test. Это критично для несбалансированного датасета: без стратификации редкий класс `other` (4.5%) мог бы случайно перекоситься в тесте, делая метрики по нему нестабильными.

Результат: **8 000 train / 2 000 test.**

## Обработка текста: NLP-пайплайн

Текст `user_message` — самый информативный признак. К нему применяется пятиступенчатый пайплайн перед подачей в TF-IDF.

### Шаг 1: нижний регистр

`text.lower()` — `"Не могу войти"` и `"не могу войти"` становятся одним токеном.

### Шаг 2: токенизация по регулярному выражению

```python
TOKEN_RE = re.compile(r"[а-яёa-z]+", re.IGNORECASE)
tokens = TOKEN_RE.findall(text)
```

Оставляем только последовательности кириллических и латинских букв. Пунктуация, цифры, эмодзи отбрасываются.

### Шаг 3: удаление стоп-слов

```python
from nltk.corpus import stopwords
RU_STOPWORDS = set(stopwords.words("russian"))  # 151 слово
```

**Зачем:** служебные слова (`и`, `в`, `не`, `что`, `как`, `или`, `бы`) встречаются во всех категориях с примерно одинаковой частотой и не помогают различать классы. Это шум, который раздувает словарь TF-IDF и размазывает сигнал.

Также отфильтровываем токены короче 2 символов — одиночные буквы бесполезны.

### Шаг 4: лемматизация через pymorphy3

```python
morph = pymorphy3.MorphAnalyzer()

def _lemma(token):
    return morph.parse(token)[0].normal_form
```

**Зачем:** в русском языке одно слово имеет десятки форм:
- `возврат`, `возврата`, `возвратом`, `возвратах`, `возвраты` → все это **одна и та же сущность**
- `купить`, `купил`, `куплю`, `купили` → **один глагол**
- `подписка`, `подписку`, `подпиской`, `подписки` → **одно слово**

Без лемматизации TF-IDF считает их **разными признаками**. Сигнал размазывается по словарю: вместо одного сильного признака «возврат» получаем пять слабых, каждый из которых редок в отдельности и рискует быть выброшен по `min_df`.

После лемматизации все формы **схлопываются в нормальную форму** (именительный падеж для существительных, инфинитив для глаголов) — признак становится **плотнее, информативнее и стабильнее** между train и test.

### Шаг 5: кэширование

На 10 000 тикетов встречается примерно **2 400 уникальных лемм**, но обращений к морфоанализатору было бы в сотни раз больше без кэша. Мы используем простой словарь `_lemma_cache: dict[str, str]` — первый вызов парсит слово, последующие возвращают готовую лемму за O(1).

```python
def _lemma(token):
    cached = _lemma_cache.get(token)
    if cached is not None:
        return cached
    lemma = morph.parse(token)[0].normal_form
    _lemma_cache[token] = lemma
    return lemma
```

**Результат:** препроцессинг 10 000 текстов завершается за **0.3 секунды**.

**Пример работы пайплайна:**

```
До:   "Хотел купить супер лайки, а у меня списало деньги со счёта и жду ответа"
После: "купить супер лайковый появиться счёт ждать ответ"
```

Видим: стоп-слова (`а`, `у`, `со`, `и`) удалены, глаголы приведены к инфинитиву (`купить`, `ждать`), существительные — к именительному падежу (`счёт`, `ответ`).

### TF-IDF

На очищенный и лемматизированный текст применяем TF-IDF-векторизацию:

```python
TfidfVectorizer(
    max_features=2000,      # широкий стартовый словарь
    ngram_range=(1, 2),     # униграммы + биграммы ("не работать", "вернуть деньги")
    min_df=5,               # токен должен встретиться в ≥5 тикетах (отсев шума)
    max_df=0.9,             # токен в >90% тикетов — авто-стоп-слово
    sublinear_tf=True,      # логарифм частоты: 10-кратное повторение != 10x важность
)
```

Получаем разреженную матрицу `8 000 × 2 000` для train и `2 000 × 2 000` для test.

## Отбор признаков

После создания полного пространства признаков применяем **двухступенчатый отбор**: сначала по L1-регуляризации на тексте, потом по важности из древесной модели на всей матрице.

### Ступень 1: L1 Logistic Regression для TF-IDF

```python
l1_selector = SelectFromModel(
    LogisticRegression(penalty="l1", solver="saga", C=1.0, max_iter=2000),
    threshold="mean",
)
tfidf_train = l1_selector.fit_transform(tfidf_train_full, y_train)
```

**Теоретическое обоснование — почему L1, а не L2:**

- **L2-регуляризация (Ridge)** штрафует сумму **квадратов** коэффициентов: `λ·Σβᵢ²`. Она уменьшает большие веса, но не зануляет их — все признаки остаются в модели.
- **L1-регуляризация (Lasso)** штрафует сумму **модулей** коэффициентов: `λ·Σ|βᵢ|`. У такой функции штрафа есть угол в нуле, и оптимизатор часто приходит именно в угол — коэффициенты неинформативных признаков **становятся строго равны нулю**. Это и есть встроенный feature selection.

`SelectFromModel` с `threshold="mean"` оставляет только признаки, у которых сумма модулей коэффициентов (по 7 классам) выше среднего по всем признакам. Фактически это двойная фильтрация: L1 зануляет слабые, `threshold` отсекает ещё и «средних».

**Выбор солвера `saga`:** `liblinear` не поддерживает многоклассовую классификацию (только OvR-обёртка), а `saga` — единственный в sklearn солвер, который поддерживает L1 + multinomial и эффективно работает на sparse-матрицах.

**Результат:** из **2 000** TF-IDF-токенов оставлено **245** (отброшено 1755, т.е. 87.75% словаря). Это огромная экономия размерности.

### Ступень 2: feature importance из ExtraTrees на всей матрице

После сборки финальной матрицы (245 TF-IDF + 13 числовых + 13 OHE = **271 признак**) применяем второй этап отбора — на этот раз по важности из древесного ансамбля:

```python
importance_selector = SelectFromModel(
    ExtraTreesClassifier(n_estimators=300, random_state=42),
    threshold="median",
)
```

**Идея:** L1-LR — линейная модель. Она отбирает признаки, которые полезны **в линейной комбинации**. Но на финальных моделях (Random Forest, LightGBM, CatBoost) признаки работают через нелинейные взаимодействия. Дополнительный отбор через деревья помогает:
- Выбросить признаки, которые были случайно включены L1 (слабая линейная корреляция, но нет разделяющей силы в разбиениях)
- Отсечь бесполезные OHE-колонки (например, редкие значения категориальных переменных)
- Сократить размерность финальных моделей — меньше переобучения, быстрее обучение

`threshold="median"` — оставляем признаки с важностью **выше медианной**, т.е. отбрасываем нижнюю половину.

**Результат:** из **271** признака оставлено **136** (отброшено 135, т.е. 49.8%).

**Итоговая размерность матрицы для обучения: 136 признаков.**

### Сравнение: что отбросили на каждом этапе

| Этап | Было | Стало | Отброшено | % |
|------|------|-------|-----------|---|
| TF-IDF до L1-отбора | 2 000 | — | — | — |
| После L1 Logistic Regression | — | 245 | 1 755 | 87.75% |
| Полная матрица (245 + 13 num + 13 OHE) | 271 | — | — | — |
| После ExtraTrees importance | — | 136 | 135 | 49.8% |

В совокупности: из потенциальных **2 026** признаков (2 000 текстовых + 13 числовых + 13 OHE) оставлено **136** — сокращение в **15 раз**. Это строгий и теоретически обоснованный отбор, который при этом улучшил метрики всех древесных моделей.

## Модели и подбор гиперпараметров

Обучаем и сравниваем **5 моделей** разных семейств.

### 1. Logistic Regression — линейный бейзлайн

**Гиперпараметры:** `GridSearchCV` по `C ∈ {0.01, 0.1, 1.0, 10.0}`, 3-fold CV, scoring=`f1_macro`.

Параметр `C` — обратная сила L2-регуляризации: маленькое `C` → сильный штраф → простая модель. Подбираем кросс-валидацией.

**Назначение в проекте:** нижний «разумный» бейзлайн. Показывает, насколько задача линейно-разделима на наших признаках.

### 2. Random Forest — бэггинг-ансамбль деревьев

**Гиперпараметры:** `GridSearchCV` по `n_estimators ∈ {200, 300}` × `min_samples_leaf ∈ {1, 2, 5}`, 3-fold CV.

**Что делает:** строит много независимых деревьев, каждое на случайной подвыборке объектов (bootstrap) и случайном подмножестве признаков в каждом узле (random subspace). Итоговое предсказание — голосование большинства.

**Плюсы:** не требует масштабирования, устойчив к выбросам, делает встроенный feature selection через `feature_importances_`, параллелится.

### 3. Extra Trees — рандомизированный бэггинг

**Гиперпараметры:** такой же `GridSearchCV` как у RF.

**Отличия от Random Forest:**
1. Разбиения в каждом узле выбираются **случайно**, а не оптимально по Gini/entropy.
2. По умолчанию — **без bootstrap**: каждое дерево учится на всём train.

**Теоретический эффект:** выше дисперсия отдельных деревьев, но ниже смещение → в задачах с высокой дисперсией признаков (как TF-IDF) часто работает лучше RF. Обучается быстрее, так как не тратит время на поиск оптимальных порогов.

**Эта же модель используется в importance-отборе на ступени 2 feature selection** (см. раздел «Отбор признаков»).

### 4. LightGBM — градиентный бустинг с leaf-wise ростом

**Гиперпараметры:** ручной перебор 4 конфигураций по сетке `learning_rate × num_leaves`:

```
{lr=0.05, num_leaves=31}, {lr=0.05, num_leaves=63}, 
{lr=0.1,  num_leaves=31}, {lr=0.1,  num_leaves=63}
```

Фиксированы: `subsample=0.8`, `colsample_bytree=0.8`, `min_child_samples=20`.

**Ключевая особенность:** в каждой конфигурации используется **early stopping с окном 50 итераций** по валидационной выборке — обучение останавливается, как только качество на валидации не растёт 50 итераций подряд. Это **автоматический подбор `n_estimators`**: не нужно задавать его сеткой.

**Что делает:** строит деревья последовательно, каждое обучается на ошибках (градиентах функции потерь) предыдущих. Использует **leaf-wise рост** (в отличие от level-wise в XGBoost): на каждом шаге расщепляет тот лист, который даст максимальное уменьшение ошибки. Это делает LightGBM быстрее и часто точнее.

### 5. CatBoost — ordered boosting + native категории

**Гиперпараметры:** ручной перебор 3 конфигураций по `learning_rate × depth`:

```
{lr=0.05, depth=6}, {lr=0.1, depth=6}, {lr=0.05, depth=8}
```

Фиксированы: `iterations=500`, `l2_leaf_reg=3`, `early_stopping_rounds=50`.

**Ключевые особенности:**

1. **Ordered boosting.** Классический бустинг страдает от prediction shift: модель видит свои же предсказания на train, что смещает оценки градиентов. CatBoost для каждого объекта строит предсказание **только по деревьям, обученным на других объектах** — как leave-one-out, но эффективно реализованный. Это снижает переобучение.

2. **Нативная работа с категориальными признаками.** Вместо OHE CatBoost применяет **target encoding с permutation-защитой от утечки**: значение категории заменяется средним таргета по этой категории, но вычисленным **только на тех объектах, что идут раньше текущего в случайной перестановке**. Для нашей задачи это значит: передаём исходные строковые `gender`, `subscription`, `platform`, `channel`, `language` через `cat_features`, и CatBoost сам делает кодирование.

**Особенность конвейера:** CatBoost получает данные в виде `pandas.DataFrame` с исходными категориями + TF-IDF-признаки как числовые колонки. OHE к нему не применяется, importance-отбор из ExtraTrees тоже не применяется (CatBoost работает с собственным полным набором признаков).

## Теоретический разбор результатов

### Почему древесные модели выросли

В сравнении с первой итерацией (без лемматизации, без L1, с chi² отбором):

| Модель | Было | Стало | Δ |
|--------|------|-------|-----|
| Random Forest | 0.9826 | **0.9850** | +0.0024 |
| LightGBM | 0.9800 | **0.9883** | +0.0083 |
| CatBoost | 0.9784 | **0.9940** | **+0.0156** |
| Extra Trees | — (не было) | **0.9894** | — |

Рост есть, и он теоретически закономерен:

1. **Лемматизация сжала TF-IDF-словарь** с 2 000 до 245 информативных токенов. Формы одного слова схлопнулись в одну лемму — **сигнал на каждый признак стал плотнее в 3–5 раз**. Дерево теперь чаще встречает «возврат» как полезный сплит, чем пять форм этого слова по отдельности.

2. **L1-отбор + importance-отбор убрали шум.** Из 2 026 признаков осталось 136 — **в 15 раз меньше**. У деревьев критичная особенность: они **легко переобучаются на шумовых признаках**, особенно со случайными локальными корреляциями. Чистое признаковое пространство → меньше переобучения → выше качество на test.

3. **Удаление `day_of_week`** убрало 7 бесполезных OHE-колонок. Категория тикета не зависит от дня недели — эти колонки работали как шум.

### Почему Logistic Regression упала

Это **самый интересный и поучительный результат** в работе. F1 macro LR: 0.8564 → **0.6752** (−0.18, падение на ~20%).

**Теоретическое объяснение:**

| | Линейные модели (LR) | Древесные ансамбли (RF, ET, LGBM, CatBoost) |
|--|--|--|
| Что любят | **высокую размерность**, sparse-признаки | **плотные, отфильтрованные** признаки |
| Риск переобучения | низкий (регуляризация + низкая выразительность) | высокий (сложность растёт с размером леса) |
| Эффект feature selection | часто **ухудшает** качество | часто **улучшает** |

Linear Regression / Logistic Regression — это фактически **взвешенная линейная сумма всех признаков**. Каждый редкий, но специфичный токен (`разблокировать`, `списалось`, `не приходит код`) даёт маленький, но целевой вклад в один из 7 классов. Регуляризация (L2 на финальной LR) сама знает, как взвесить много слабых признаков.

Когда мы выкинули **89% словаря L1-отбором**, а потом ещё **50% остатка** — importance-фильтром от деревьев, мы лишили линейную модель значительной части **разделяющих измерений**. Особенно пострадал редкий класс `other`: его специфичная лексика попала под отсев, и модель его просто перестала видеть (recall = 1%).

**CV-скор подтверждает диагноз:** `CV f1_macro=0.5797` — то есть проблема была уже на фолдах, это не переобучение на конкретном тесте, а системная потеря сигнала.

**Что это означает с точки зрения теории:**

Feature selection — это не универсальное «всегда улучшает». Это **часть гиперпараметров конкретной модели**. Отобранный набор признаков оптимален для тех моделей, на которых мы его отбирали (L1-LR для текста, ExtraTrees для всей матрицы) и близких к ним по геометрии (другие деревья). Для принципиально другой модели (L2-LR на 136 признаках) этот набор субоптимален.

Вывод корректный и важный: **агрессивный отбор признаков помогает ансамблям деревьев, но вредит бейзлайну на логистической регрессии**. Это не баг — это фундаментальное различие между моделями с низкой и высокой выразительностью.

### Почему CatBoost стал лидером

CatBoost вырос с 0.9784 до **0.9940** — самый большой прирост среди всех моделей. Причины:

1. **Native target encoding категорий.** CatBoost получает `gender`, `subscription`, `platform`, `channel`, `language` как строки и делает ordered target encoding. Это богаче, чем OHE: у других моделей `subscription=premium` — это одна бинарная колонка, а у CatBoost — это число, равное средней вероятности каждого класса среди premium-пользователей (с anti-leak permutation).

2. **Ordered boosting снижает смещение.** Классический бустинг переобучается, потому что каждое следующее дерево видит предсказания предыдущих, сделанные на тех же данных. CatBoost использует **независимые permutation-модели** для предсказаний на train → оценки градиентов честные → меньше переобучения.

3. **Работа с лемматизированным TF-IDF как числовыми признаками.** Это ему тоже далось лучше, чем другим: target encoding категорий ловит остаточный сигнал, не захваченный TF-IDF.

Цена — **130 секунд обучения против 3.3–5 секунд у других моделей** (в ~40 раз дольше). В продакшене это критично.

## Выводы и практические рекомендации

### По задаче

1. **Задача в целом хорошо решаема** — все древесные ансамбли достигают F1 macro > 0.98. Текст обращения содержит сильные тематические маркеры, которых достаточно для надёжного роутинга.

2. **Лемматизация и осмысленный feature selection дают реальный прирост** — CatBoost вырос на +1.6 п.п., LightGBM на +0.8 п.п. В задачах с русским текстом без лемматизации не обойтись: сильно теряется в качестве.

3. **Logistic Regression — плохой выбор при агрессивном feature selection**, но отличный бейзлайн на полной матрице признаков. В этом проекте она играет роль **теоретического контрпримера**, показывающего границы применимости отбора признаков.

### По моделям

**Итоговый рейтинг по F1 macro:**

1. **CatBoost** — 0.9940 (лучшее качество, но медленный)
2. **Extra Trees** — 0.9894 (лучший компромисс качество/скорость)
3. **LightGBM** — 0.9883 (самый быстрый из топовых)
4. **Random Forest** — 0.9850 (крепкий baseline)
5. **Logistic Regression** — 0.6752 (страдает от агрессивного feature selection)

### Практическая рекомендация

**Для боевого продакшена — LightGBM:**
- F1 macro 0.9883 отличается от CatBoost (0.9940) всего на 0.6 п.п., но
- обучается в **40 раз быстрее** (3.3 с vs 130.6 с)
- лёгкий инференс, маленький размер модели на диске
- стабильная поддержка в экосистеме MLOps

**Резервный простой вариант — Extra Trees:** почти не отстаёт от LightGBM (0.9894), не требует тюнинга гиперпараметров, работает из коробки.

**CatBoost** оправдан только когда нужно выжать последние десятые доли процента качества и время обучения некритично (например, переобучение раз в неделю на продакшене).

**Logistic Regression** подходит как **лёгкий бейзлайн** для проверки пайплайна, но её стоит учить **на полной матрице признаков** (без агрессивного отбора), если нужна осмысленная метрика.
